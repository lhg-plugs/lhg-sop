# sop-audit：SOP 评审与版本管理

> 目标：SOP 发布前，把"写出来没人能用"的问题全部消灭。
> 核心纪律：**脚本先行、试读为王；blocker 清零才可用；为清零改规则是作弊。**

## 1. 何时使用

- SOP 初稿完成、准备发布时 → 必须跑完本 skill
- `/lhg-sop:audit` 命令全程按本 skill 执行
- SOP 到了复审日期 → 用本 skill 做定期评审（重点看第 7 节版本纪律）

## 2. 输入与输出

- **输入**：SOP 文档目录（默认 `sops/`）
- **输出**：`sops/audit-YYYYMMDD.md` 分级审计报告，结论为"可用 / 不可用"

## 3. 确定性脚本审计（机器部分，零 LLM 成本）

```bash
python3 scripts/audit/sop_audit.py --target sops/ --format text
```

脚本扫描 Markdown 格式的 SOP，规则分三级：

- **blocker**（必须修，否则 SOP 无法用）：
- SOP-HDR-001：文档头缺版本/日期/责任人
- SOP-PUR-001：无"目的"节 ｜ SOP-SCP-001：无"范围"节
- SOP-SEQ-001：步骤编号不连续 ｜ SOP-OWN-001：步骤无责任人
- **warning**（修或写豁免理由）：
- SOP-CHK-001 检查项含模糊词 / SOP-CHK-002 检查项无检查人
- SOP-PRE-001 无前置条件 / SOP-EXC-001 无例外与升级路径
- SOP-OUT-001 无交付物说明 / SOP-TRM-001 术语不一致
- SOP-IMP-001 步骤含多动作 / SOP-VER-001 版本与修订历史不一致
- **nit**（顺手修）：步骤过长、复审日期缺失等细节

发现分三级处理：blocker 逐条修（修一条复查一条）；warning 修掉或写豁免理由；nit 顺手修。

## 4. blocker 修复手册

### 4.1 SOP-HDR-001：文档头缺三要素

- 根因：写的时候图省事，只写了标题。
- 修复：按 sop-writing 第 4 节模板补齐"编号/版本/生效日期/下次复审/责任人/批准人"。
- 验证：规则消失；责任人是真人真名，不是"相关部门"。

### 4.2 SOP-SEQ-001：步骤编号不连续

- 根因：删步骤时没重编号，或从两份文档拼步骤。
- 修复：重排为 1,2,3…连续编号；分支跳转的目标编号同步更新。
- 验证：规则消失；人工通读一遍跳转逻辑。

### 4.3 SOP-OWN-001：步骤无责任人

- 根因：写"客服/调度配合完成"，没说清到底谁干。
- 修复：每步开头加【责任人】，责任人必须出自"角色与职责"表；"配合"拆成两步各写各的。
- 验证：规则消失；没有"共同负责"（共同负责=没人负责）。

## 5. 人工评审清单（脚本抓不到的，人来审）

### 5.1 新人试读（SOP 唯一的真金标准）

找个**没做过这个流程的人**，让他照着 SOP 做一遍（或口述他会怎么做），记录所有卡住的地方：

- [] 有没有"这一步我不知道去哪找/找谁"的卡点？
- [] 有没有"这句话我看不懂"的术语？
- [] 有没有"做到这里发现前面漏了什么"的断层？
- [] 全程用时多久？和预期差多少？

试读发现的每个卡点都是 blocker 级别的问题，修完再找另一个人试读，直到零卡点。

### 5.2 术语一致性

- [] 同一概念全文只用一个词吗？（"工单"和"任务单"混用是最常见的）
- [] 缩写首次出现展开了吗？
- [] 术语表（第 5 节）覆盖了所有内部黑话吗？

### 5.3 分支与异常

- [] 每个分支的判断条件都是可观察的吗？
- [] 异常处理写的是"找谁+有时限"，而不是"及时上报"吗？
- [] 禁忌清单有吗？（"千万不能…"）

## 6. 审计报告模板

```markdown
# SOP 审计报告（2026-10-11）
- 范围：sops/ 下 X 份 SOP
- 脚本审计：blocker X / warning Y / nit Z（详见附表）
- 新人试读：试读人 ____，卡点 X 个（已修/待修）
- 需人工确认项：（如责任人涉及组织架构调整）
- 结论：可用 / 不可用
```

结论只能是"可用"或"不可用"，不许写"基本没问题"。

## 7. 版本管理纪律（复审时查）

- 每份 SOP 都有下次复审日期吗？过期没复审的列出来。
- 修订历史与文档头版本号一致吗？（SOP-VER-001）
- 旧版归档了吗？`sops/archive/` 里能找到上一版吗？
- 检查清单与 SOP 版本绑定吗？（清单头部的对应版本号）

## 7.5 定期复审流程（每季度一次）

1. 拉出所有过了复审日期的 SOP 清单。
2. 问责任人三个问题：流程变了吗？出过事吗？一线还在用吗？
3. 三个答案都是"否" → 只更新复审日期到下一季度（小版本）。
4. 任一答案为"是" → 走完整修订流程（访谈→改版→审计→试读）。
5. 连续两个季度"三否"的 SOP，考虑降级为检查清单（说明流程已稳定，不需要 SOP 的重量）。

复审不是走过场：每次复审必须留记录（谁审的、结论是什么），审计时抽查。

## 8. 反模式

1. **只跑脚本不试读**：脚本查的是文档结构，"新人照着能不能做出来"只能试读验证。
2. **自己人试读**：老员工试读等于没试读（他脑子里有隐性知识，会自动脑补）。
3. **warning 全豁免**：豁免理由写"先这样"等于没审。
4. **修完不复查**：修一条，脚本复查一条，试读卡点回归验证一遍。
5. **发布了就不管**：SOP 没有复审日期，半年后变成废纸，还不如不写。

## 9. 自检与反馈

质检门（审计阶段）：
- [] 脚本跑了吗？blocker 清零了吗？
- [] 新人试读做了吗？卡点清零了吗？
- [] 报告存档了吗？结论是二选一的"可用/不可用"吗？
- [] 版本纪律 7 节逐项检查了吗？

标准冒烟用例：用 fixtures/sop-bad 跑脚本，SOP-SEQ-001 / SOP-OWN-001 / SOP-HDR-001 / SOP-PUR-001 四个 blocker 必须全部命中。

发现 bug 或有改进建议，以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-sop/issues，正文写清"复现步骤 → 实际表现 → 期望表现"。
